SHARC-ALSA Example

Note

SHARC-ALSA is currently only supported on SC598

Warning

For releases prior to 3.0.0, follow SHARC-ALSA example (legacy) (wiki.analog.com)

Note

SHARC-ALSA is not enabled by default when following the Getting Started guides within the release pages (3.0.0 or higher). The default build enables linux_only_audio, and only one audio mode can be selected. Before building the image, add the following lines to conf/auto.conf within the build directory. kas regenerates conf/local.conf, so changes made there are lost.

DISTRO_FEATURES:remove = "linux_only_audio"
DISTRO_FEATURES:append = " adi_sharc_alsa_audio"
IMAGE_INSTALL:append = " linux-firmware-sharc-alsa alsa-utils alsa-lib"

The IMAGE_INSTALL line installs ALSA and the test audio file used below. adi_sharc_alsa_audio installs the SHARC firmware, in /lib/firmware/adi.

Introduction

SHARC-ALSA is a framework designed to make a SHARC appear as an audio device in ALSA. It uses RPMsg for the communication between the ARM Core and the SHARC Core. When playing audio through ALSA the audio samples are transferred to the SHARC where additional processing can take place before the audio is played.

SHARC-ALSA modes

There are 2 modes for SHARC-ALSA, and they differ in how the SHARCs are programmed. The mode is set in the conf/auto.conf file, when building the Linux image, in place of the default linux_only_audio. E.g. : DISTRO_FEATURES:remove = "linux_only_audio" and DISTRO_FEATURES:append = " adi_sharc_alsa_audio"

  • adi_sharc_alsa_audio

    Audio playback handled through SHARC firmware, no codec control (volume, etc) from Linux. remoteproc is used to load the SHARC LDR firmware files.

  • adi_sharc_alsa_audio_uboot

    Audio playback handled through SHARC firmware, no codec control (volume, etc) from Linux. rproc within U-Boot is used to load the SHARC LDR firmware file.

Programming the SHARC

Using Linux (remoteproc)

The example SHARC images are in the /lib/firmware/adi directory on the target, icap_sharc_alsa_core1.ldr for SHARC core 1 (remoteproc0) and icap_sharc_alsa_core2.ldr for SHARC core 2 (remoteproc1). The SHARCs are running already when Linux has booted, with remoteproc having loaded these images, so you can stop them, reload the example image or your own one, and start them again. Firmware names are relative to /lib/firmware.

~$

echo stop > /sys/class/remoteproc/remoteproc0/state

snd_soc_sharc_alsa_asoc_card virtio0.sharc-alsa.-1.21: sharc-alsa card removed for rpmsg endpoint addr: 0x015
ADI Reset Control Unit 3108c000.rcu: Timeout waiting for remote core 1 to IDLE!
remoteproc remoteproc0: stopped remote processor sharc

~$

echo adi/icap_sharc_alsa_core1.ldr > /sys/class/remoteproc/remoteproc0/firmware

~$

echo start > /sys/class/remoteproc/remoteproc0/state

remoteproc remoteproc0: powering up sharc
remoteproc remoteproc0: Booting fw image adi/icap_sharc_alsa_core1.ldr, size 132860
virtio_rpmsg_bus virtio0: rpmsg host is online
virtio_rpmsg_bus virtio0: creating channel sharc-alsa addr 0x15
snd_soc_sharc_alsa_asoc_card virtio0.sharc-alsa.-1.21: sharc-alsa card probed for rpmsg endpoint addr: 0x015
rproc-virtio rproc-virtio.0.auto: registered virtio0 (type 7)
remoteproc remoteproc0: remote processor sharc is now up

When executing the echo start command you will notice the LEDs on the SOMCRR-EZKIT flashing and then settle on LED7 remaining on. This indicates that the image on the SHARC is running.

Using U-Boot (rproc)

An example SHARC image is present within this repository. The SHARC can be programmed with this image via U-Boot. You need to store icap-sharc-alsa_Core1.ldr & icap-sharc-alsa_Core2.ldr (or your own image/images) in the TFTP server as demonstrated in Setting Up Your Host PC: Configure TFTP Service. Copy these using the following command, executed from your build folder:

~$

cp ../sources/meta-adi/meta-adi-adsp-sc5xx/recipes-icc/sharc-audio/files/icap-sharc-alsa_Core{1,2}.ldr \
   /tftpboot/

With these stored in the TFTP server, you need to input the following at the U-Boot prompt:

=> rproc init
=> tftp ${loadaddr} icap-sharc-alsa_Core1.ldr
=> rproc load 0 ${loadaddr} ${filesize}
Load Remote Processor 0 with data@addr=0x96000000 132860 bytes: Success!
=> tftp ${loadaddr} icap-sharc-alsa_Core2.ldr
=> rproc load 1 ${loadaddr} ${filesize}
Load Remote Processor 1 with data@addr=0x96000000 79892 bytes: Success!
=> rproc start 1
=> rproc start 0

You can now proceed to booting Linux as per usual. The SHARCs will be programmed and running.

Playing Audio

Note

The audio from the SHARC is routed to DAC1/2. Connect a set of speakers to J17 also labelled as DAC1/2.

Play back the audio sample file stored in /usr/share/sounds/alsa/

~$

aplay /usr/share/sounds/alsa/2Ch_L440_R200_48kHz_16bit_6s.wav

You will hear a 440Hz tone on the left channel and a 200Hz tone on the right channel being played for 6 seconds.

Recording Audio

The example SHARC images have no command interface for adding a tone to the audio. Each SHARC registers one sharc-alsa RPMsg channel, which the sharc-alsa ASoC driver turns into a sound card:

~$

ls /sys/bus/rpmsg/devices/

virtio0.rpmsg_ctrl.0.0    virtio0.rpmsg_ns.53.53    virtio0.sharc-alsa.-1.21
virtio1.rpmsg_ctrl.0.0    virtio1.rpmsg_ns.53.53    virtio1.sharc-alsa.-1.22

~$

aplay -l

**** List of PLAYBACK Hardware Devices ****
card 0: sharcalsacard21 [sharc-alsa-card_21], device 0: sharc-alsa-playback-336 sharc-alsa-codec-dai_336-0 []

~$

arecord -l

**** List of CAPTURE Hardware Devices ****
card 1: sharcalsacard22 [sharc-alsa-card_22], device 0: sharc-alsa-capture-352 sharc-alsa-codec-dai_352-0 []

SHARC core 1 provides the playback card, card 0, and SHARC core 2 the capture card, card 1, which records from the ADC. Both cards take 32-bit, 2 channel, 48 kHz audio; the plughw device converts other formats. To record 5 seconds of audio:

~$

arecord -D plughw:1,0 -d 5 -f S16_LE -c 2 -r 48000 /tmp/capture.wav

Recording WAVE '/tmp/capture.wav' : Signed 16 bit Little Endian, Rate 48000 Hz, Stereo
